\paragraph{How it is configured.}
\begin{itemize}[nosep]
  \item \textbf{Restart behavior:} both containers use \texttt{restart: unless-stopped}, so they return after a reboot or a Docker restart.
  \item \textbf{Persistent data:} the named volume \texttt{gitea\_gitea\_data} holds Gitea's repositories and SQLite database at \texttt{/data}; \texttt{gitea\_caddy\_data} keeps Caddy's certificates and ACME account; \texttt{gitea\_caddy\_config} holds Caddy's saved configuration. The \texttt{Caddyfile} is mounted read-only from the project directory.
  \item \textbf{Proxy connection:} Caddy and Gitea share the private Compose network \texttt{gitea\_web}; Caddy reaches Gitea at \texttt{gitea:3000} by service name. Gitea has no \texttt{ports:} entry, so it is not published on the host; only Caddy publishes 80 and 443.
  \item \textbf{Non-secret configuration (environment variables):} SQLite database at \texttt{/data/gitea/gitea.db}; \texttt{DOMAIN} and \texttt{ROOT\_URL} set to the HTTPS hostname; Gitea's own SSH server disabled (Git over HTTPS only); web installer skipped (\texttt{INSTALL\_LOCK}); self-registration disabled.
  \item \textbf{Secrets:} none appear in the Compose file, the \texttt{.env} file (hostname and image versions only), or this document. The first administrator password was generated once in the administrator's own terminal and stored in a password manager.
\end{itemize}

\subsubsection{Decision: SQLite}
Group~1 uses Gitea's built-in SQLite database \cite{GiteaDBPrep}. This was a
team decision recorded on October 12, 2026. Reasons:
\begin{itemize}[nosep]
  \item The startup has two members; Gitea's write load is a few pushes,
  issues, and reviews per day, well within SQLite's capability.
  \item No second container, database port, or database credential exists, so
  there is nothing extra to secure, patch, or expose.
  \item The whole service state (database file and repositories) lives in one
  volume, which keeps a future backup simple.
\end{itemize}
\textbf{Limitation.} SQLite serialises writes in a single file. A larger team
with many concurrent pushes, or a deployment that runs several Gitea instances
behind a load balancer, should move to PostgreSQL in its own container
\cite{DosManual}.

\subsubsection{Settings}
The database is configured with environment variables in the versioned
Compose file (\href{\RepoURL/blob/main/assignment-4/gitea/docker-compose.yml}{\texttt{gitea/docker-compose.yml}}),
which Gitea writes into \texttt{/data/gitea/conf/app.ini} at start-up
\cite{GiteaConfig}:
\begin{minted}{yaml}
services:
  gitea:
    environment:
      GITEA__database__DB_TYPE: sqlite3
      GITEA__database__PATH: /data/gitea/gitea.db
    volumes:
      - gitea_data:/data        # named volume, outside the container layer
    # no ports: Gitea is reached only by Caddy on the private network
volumes:
  gitea_data:
\end{minted}

Because the volume is mounted from Docker's volume store, it is \emph{outside}
the container's disposable writable layer: removing or recreating the
container does not touch it. Only an explicit \texttt{docker compose down -v}
or \texttt{docker volume rm} deletes it, and both are forbidden in the team's
runbook (Section~\ref{Section:giteaArchitecture}).

\subsubsection{Persistence test procedure}
The test is scripted in
\href{\RepoURL/blob/main/assignment-4/sd/persistence-test.sh}{\texttt{assignment-4/sd/persistence-test.sh}}
so it can be repeated exactly. Run on the Docker host from
\texttt{assignment-4/gitea}, it:
\begin{enumerate}[nosep]
  \item creates repository \texttt{persistence-check} (with an initial README
  commit) and issue \#1 through the Gitea API, unless they already exist;
  \item records the container ID and creation time, the volume mount, the
  database file, and the repository, issue, and \texttt{main} commit IDs;
  \item replaces \emph{only} the Gitea container, keeping volumes:
\begin{minted}{bash}
docker compose up -d --force-recreate gitea
\end{minted}
  \item waits for the health check, then records the same items again.
\end{enumerate}
The password is read from the terminal and never printed.

data exists outside the volume, so losing the volume or the VM disk would
still lose the data (see Section~\ref{Section:giteaArchitecture}).

\paragraph{HTTP to HTTPS redirect.}

\paragraph{Renewal.}
Caddy renews its certificates automatically before they expire; Let's Encrypt
certificates last 90 days, so the first renewal is due about two months after
issue \cite{CaddyAutoHTTPS}. Caddy's log already recorded the renewal window
reported by the certificate authority (ACME Renewal Information), and the
certificate and account are stored in the persistent volume
\texttt{gitea\_caddy\_data}, so a container replacement does not lose them.
\paragraph{Renewal test (staging dry run).}
Caddy has no renew-now or dry-run command that we know of, so the test used the
idea behind a certbot dry run: run the same ACME process against Let's
Encrypt's \emph{staging} server, which issues untrusted test certificates and
does not touch the production certificate (\ListRef{42}, October 15, 2026,
19:03 to 19:08 UTC). Three attempts were needed, and all are reported.
\begin{enumerate}[nosep]
  \item \textbf{Staging CA for the real hostname: inconclusive.} Adding a global staging CA and reloading Caddy produced no new order. Caddy already held a valid certificate for the name, kept serving it (same thumbprint), and logged only that automatic TLS was enabled. This proved nothing about renewal, and the production configuration was restored at once.
  \item \textbf{Wrong directive: rejected.} The first version of the test block used \texttt{ca} inside the ACME issuer, which Caddy rejected (``unrecognized ACME issuer property: ca'') and kept its previous working configuration, so the live site was unaffected. The correct directive is \texttt{dir}.
  \item \textbf{Throwaway hostname with a staging-only issuer: succeeded.} A second site block was added for \texttt{52-73-254-36.sslip.io} (a public wildcard-DNS name that resolves to the server's address), configured with the staging directory, and the production block was left unchanged. Within about five seconds of the reload Caddy created an ACME account, solved the TLS-ALPN-01 challenge, finalized the order, downloaded the chain, and logged ``certificate obtained successfully'' with the staging issuer. The server then presented that certificate for the test name (issuer ``(STAGING) Artificial Amaranth YE1'', not trusted by Windows, as expected) while the production certificate stayed identical (same thumbprint).
\end{enumerate}
The production Caddyfile was then restored (its SHA-256 matches the repository
copy), the test certificate and backup file were removed, and normal checks
confirmed the redirect, an HTTP 200 response, and the original production
certificate (\ListRef{42}).

\paragraph{Why HTTPS does not replace a firewall.}
HTTPS protects the content of a connection between a browser and Caddy; it says
nothing about which ports exist or who may connect to them. Without the
security group, ports such as 22, 3000, or 2019 would accept connections from
the whole internet, and encryption on port 443 would not help. The firewall
decides which services can be reached at all; TLS only protects the ones that
are reachable. The two address different risks, so both are needed
\cite{DosManual}.

\subsubsection{Request path}
\begin{enumerate}[nosep]
  \item The browser resolves \GiteaHost{} through public DNS (an \texttt{A}
  record at Name.com, TTL 300; no \texttt{AAAA} record) to the instance's
  Elastic IP and connects on 443.
  \item The security group admits 443 and 80 from anywhere and 22 only from
  the approved address; everything else is dropped.
  \item Caddy terminates TLS with a Let's Encrypt certificate for
  \GiteaHost{}, obtained with the TLS-ALPN-01 challenge on port 443 and
  stored in the \texttt{gitea\_caddy\_data} volume. A request on port 80
  receives \texttt{308 Permanent Redirect} to HTTPS.
  \item Caddy forwards the request as plain HTTP over the private Compose
  network \texttt{gitea\_web} to \texttt{gitea:3000}, found by service name.
  \item Gitea reads and writes the SQLite file and the bare Git repositories
  in the \texttt{gitea\_gitea\_data} volume and answers through Caddy.
\end{enumerate}
Git clone and push use the same HTTPS path; Gitea's own SSH clone is disabled
(\texttt{DISABLE\_SSH=true}). The image's \texttt{sshd} still listens on port
22 \emph{inside} the container, but that port is not published.

\subsubsection{Administration path}
Administrators connect with SSH keys only, as \texttt{ec2-user}, from the
approved address. Each member has a separate key, and the server's
\texttt{sshd} log tells them apart by key fingerprint. Before the first
connection, each member compared the server's host key with the one published
by the administrator (\texttt{SHA256:sJSqc/LAVTJ\ldots buvgosM}). Docker is
run by \texttt{ec2-user}, which is in the \texttt{docker} group.

\subsubsection{Where data lives}
All Gitea state is in the named volume \texttt{gitea\_gitea\_data}
(Table~\ref{Table:GiteaDataLocations}); TLS certificates and the ACME account
are in \texttt{gitea\_caddy\_data}, and Caddy's runtime configuration in
\texttt{gitea\_caddy\_config}. The volumes are on the instance's 20\,GB
\texttt{gp3} root disk. Containers hold no state and can be replaced at any
time; row~3 did exactly that.

\subsubsection{Operating runbook}
All commands run on the instance from \texttt{\textasciitilde/gitea}.
\begin{minted}{bash}
docker compose ps                      # both services Up; gitea (healthy)
docker compose logs --tail=100 gitea   # application errors
docker compose logs --tail=100 caddy   # TLS issuance/renewal, proxy errors

docker compose up -d --force-recreate gitea   # replace the container, keep volumes
docker compose up -d                   # re-apply the Compose file after a change
curl -sS -o /dev/null -w "%{http_code}\n" https://git.ssw590-g1.tech/api/healthz

\subsubsection{Persistence is not backup}
The persistence test (Section~\ref{Section:giteaDatabase}) proves data
survives a \emph{container} replacement because it lives on a volume. A backup
is a separate copy of that data, stored elsewhere, that has been restored
successfully. Without one, deleting the volume, terminating the instance (its
root disk has \texttt{DeleteOnTermination=true}), or corrupting the database
still loses everything. A verified backup and restore is the optional extra
credit (Section~\ref{Section:giteaExtraCredit}).
