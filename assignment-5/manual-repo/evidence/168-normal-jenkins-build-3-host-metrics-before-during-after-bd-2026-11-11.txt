- CPU: the only sample containing the 2.4 s build reads 10.1 %, against 4.0-6.7 % in the minutes before and 6.2 and 4.5 % after. A one-core job of 2.4 s adds about
  2.4 / (30 s * 2 CPUs) = 4 percentage points to a 30 s average, so a rise from about 5-6 % to 10 % is of the size expected for this build. It is one sample, however,
  and its neighbours already vary between 3.1 and 6.7 %, so it cannot be called proof.
- Memory: MemAvailable moved from 671 MiB to 662 and 654 MiB, then back to 662 and 695 MiB: changes of 10-40 MiB are within the ordinary movement of the previous
  minutes (632-678 MiB), so no memory effect of the build can be separated from the noise.
- Why so little is visible: the build took 2.4 s and Prometheus samples every 30 s, so it falls inside one scrape interval and is averaged with 27 quiet seconds.
  A longer or heavier build would be needed to see a clear shape; the pipeline is two short Python commands (py_compile and two unit tests).
- Whole-host correlation does not attribute CPU or memory to Jenkins or to any individual container; the figures above are for the whole host.
  Jenkins ran on the controller, so its use is inside this host's measurements (a remote agent's would not be).
