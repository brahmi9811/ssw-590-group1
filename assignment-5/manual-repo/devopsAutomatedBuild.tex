\paragraph{Why the runner needs no public submission port.}
The runner works by pulling: it connects out to Gitea over HTTPS, asks for waiting jobs, and reports the log and
result back over the same connection. Gitea never opens a connection to the runner, and a push goes to Gitea, not to
the runner. The runner container therefore publishes no port at all (the \texttt{Ports} column of \texttt{docker ps}
is empty for it, and the only published ports on the host remain Caddy's 80 and 443).

on \texttt{main} and \texttt{build.yml (on: push)} (\FigRef{53}). Run~\#1 compiled the manual but failed at the

\paragraph{Decision: same host.}
Three options were compared on October 19, 2026: the runner on the Gitea host (chosen), a larger instance, or a
laptop. The Gitea host costs nothing extra and stays online for the instructor and TA; the risks are the small
memory and the shared disk. Observed: run~\#2 took 1~minute 11~seconds, Gitea stayed healthy, and swap use was
about 110~MB afterwards.

\paragraph{Isolation and ports.}
The runner container publishes no port; the only host ports open to the internet are still 80 and 443 on Caddy.
Jobs run in their own containers on a fresh network per job; the runner is not run in privileged mode, and no host
volumes are allowed for jobs (the configuration sets no \texttt{valid\_volumes}). Whether a workflow can still
reach the Docker socket was \emph{not} tested; the risk is discussed in Section~\ref{Section:buildSecretBoundary}.

\paragraph{Failed attempts and corrections.}
Registration took four attempts on October 19, 2026; the first three failed. Attempt~1 was rejected: Gitea
answered ``runner registration token not found'' and the runner retried in a loop; the container was stopped and
the token file on the server was emptied. The script was changed to report how many characters it received, and
attempt~2 showed the cause: only \emph{one} character of the 40-character token arrived, because pasting into a
hidden terminal prompt kept only the first character. The script was changed again to read the token one key at a
time, but attempt~3 still read one character; the script stopped on the administrator's machine before sending
anything. The third change reads the token from the clipboard (which holds the full 40 characters, as checked
with a length-only command) and refuses to send anything shorter than 20 characters. Attempt~4 printed
\texttt{Runner registered successfully}. Afterwards the token file was emptied again (0~bytes, mode 600) and the
runner restarted without it. The token itself is never written in this manual.

\subsubsection{Failure detection}
The build fails, and no artifact is uploaded, when:
\begin{itemize}[nosep]
  \item \texttt{pdflatex} reports any error: \texttt{-halt-on-error} stops it and \texttt{latexmk} exits non-zero;
  \item \texttt{devopsITManual.pdf} is missing or empty;
  \item the final pass still reports undefined or multiply defined references;
  \item the build identifier is not in the LaTeX log (row~4);
  \item no PDF matches the upload path (\texttt{if-no-files-found: error}).
\end{itemize}
Before pushing, the same commands were run in the same image on SD's
workstation (\texttt{ci/local-build.sh}): a clean build took about 18~seconds,
and a copy with an undefined command inserted exited with code~1, reported
``Undefined control sequence'' with the line number, and produced no PDF.

\subsubsection{Checkout and artifact path}
The runner polls Gitea over HTTPS for work. In the job container,
\path{actions/checkout} fetches the triggering commit from
\path{https://git.ssw590-g1.tech}, and \path{actions/upload-artifact} sends
the PDF back to the same run over HTTPS. Gitea and the job share no
filesystem.

\subsection{PDF version traceability (15 points)}
\label{Section:buildTraceability}
\index{build identifier}
\index{artifact}
\textbf{Owner:} SD. \textbf{Status:} identifier verified on the PDF
downloaded from run~\#2 \StatusPass.

The human-maintained version stays \texttt{\string\DocumentVersion} in
\texttt{devopsITManual.tex}, changed only by a person with a history entry. The
workflow appends a build suffix
\texttt{+build.<run\_number>.<first 7 characters of the commit>}, taken from
Gitea's \texttt{gitea.run\_number} and \texttt{gitea.sha} \cite{GiteaActionsVars}.
It reaches LaTeX through \texttt{latexmk -usepretex}, which defines
\texttt{\string\BuildSuffix}, \texttt{\string\BuildRun}, and
\texttt{\string\BuildCommit} before the main file is read. The main file
provides \texttt{+local} as the default, so a local build is clearly
unofficial. The suffix appears on the title page and in every page footer, and
is written to the LaTeX log, where the workflow checks it.

Nothing is written back to the repository: the identifier exists only inside
the generated PDF and the run's log, so a build cannot trigger another push.
This PDF itself shows \textbf{Version \DocumentVersion\BuildSuffix}.

\paragraph{An artifact is not a backup.}
Artifacts expire and live on the same disk as Gitea; deleting the run or the repository removes them, and the
server has no backup (the optional backup test of Chapter~2 was not attempted). The permanent copies are the
LaTeX source in Git (which can rebuild any version from its commit) and the PDF that the team submits to the
course. The artifact is a delivery path, not storage.

\subsection{Runner and secret boundary (5 points)}
\label{Section:buildSecretBoundary}
\textbf{Owner:} BD. \textbf{Status:} described from the observed configuration; the Docker-socket limits below were not tested \StatusPass.

\paragraph{Who can edit the workflow.}
A workflow is code that the runner executes, so whoever can push to \texttt{group1-startup/manual} controls what
runs. Two people can: BD (organization owner) and SD (collaborator with \emph{Write}, \FigRef{51}). The team
\texttt{developers} also has the Actions unit, and registration on this Gitea is closed
(\texttt{DISABLE\_REGISTRATION}), so no outsider can create an account, fork the repository, or open a pull
request. \textbf{Limitation:} \texttt{main} of this repository has no branch protection (unlike \texttt{twintrack}),
so either member can push a workflow change that runs immediately without review; this is accepted for a
two-person team and was not changed.

\begin{figure}[htbp]
\centering
\includegraphics[width=\linewidth]{evidence/51-gitea-manual-repo-collaborators-sakshi-write-teams-owners-developers-2026-10-19.png}
\caption{Settings, Collaborators of \texttt{group1-startup/manual}, October 19, 2026: \texttt{sakshi} with Write; teams \texttt{Owners} (Owner) and \texttt{developers} (unit permissions Code, Issues, Pull Requests, Releases, Wiki, Projects, Packages, Actions).}
\label{Fig:E51}
\end{figure}

\paragraph{Where the secrets are.}
\begin{itemize}
\item \emph{Runner registration token} (hint only): shown in Gitea's Site Administration, Actions, Runners page;
  BD copies it into the clipboard and a script on BD's machine sends it over SSH to a root-only file on the
  server (mode 600). After a successful registration the file was emptied (0~bytes) and the runner was restarted
  without it; the registration itself is kept in the Docker volume. The token is not in the repository, the
  workflow, the logs, or this PDF. If it leaks, reset it on the same page.
\item \emph{Repository secrets:} none. The workflow uses no secret and no access token of its own.
\item \emph{Gitea access token} used once to create the repository: deleted right after use.
\end{itemize}

\paragraph{Docker privilege risk.}
The runner container mounts the host's Docker socket (Listing~\ref{Listing:RunnerCompose}) so that it can create job
containers. Anyone who controls the runner process can start any container on the host, which also holds Gitea's
data volume; that is root-equivalent on this host, the same host that serves the team's Gitea
\cite{GiteaRunnerDocker}. The jobs themselves are not given the socket: the configuration sets
\texttt{privileged: false} and no \texttt{valid\_volumes}, which by design keeps a workflow from mounting host
paths. \emph{This was not tested}, so the manual does not claim it as verified. Compensating controls: only two
trusted people can edit workflows, there are no outside accounts, no repository secrets exist to steal, and the
runner publishes no port. A stronger design would use a separate runner host, which was not chosen because of
cost.

\paragraph{Why untrusted workflow changes must not get privileged access or secrets.}
A pull request from a stranger could rewrite the workflow to run any command in the job, read every secret the
job can see, and, with Docker access, attack the host and the other containers. Therefore this runner is
registered only for this repository's trusted authors, holds no secrets, and must never be given privileged mode,
host mounts, or secrets while outsiders can propose workflow changes.

\paragraph{Third-party code in the build.}
The workflow's two steps \texttt{actions/checkout} and \texttt{actions/upload-artifact} are fetched from
github.com at the time of each run (the \emph{Set up job} log, \FigRef{57}, shows the clone), selected by a version
tag that its owner can move. This is a supply-chain dependency that was accepted for simplicity; pinning each
action to a commit hash is a possible improvement.

\paragraph{Non-secret configuration.}
The runner's Compose file and configuration are printed in Section~\ref{Section:buildRunner}
(Listings~\ref{Listing:RunnerCompose} and~\ref{Listing:RunnerConfig}) and are kept in the repository under
\texttt{config/runner/}. Hosts and Passwords tables: \textbf{updated} for the runner (\ChapterRef{HostsPasswords}).

\subsubsection{Failed-build troubleshooting}
\index{troubleshooting!failed build}
\begin{enumerate}[nosep]
  \item Open the failed run in Gitea (\emph{Actions} tab) and expand the first red step.
  \item Compile step failed: search the log for the first line starting with \texttt{!}; the following \texttt{l.<n>} gives the file line. Fix it and run \texttt{ci/local-build.sh} before pushing again.
  \item ``PDF is missing'' or ``build identifier not found'': the compile ended early or \texttt{-usepretex} was changed; compare with the workflow in Section~\ref{Section:buildCompilation}.
  \item Job never starts (``waiting for a runner''): the runner is offline or its label is not \texttt{manual-builder}; ask the runner owner (Section~\ref{Section:buildRunner}).
  \item Checkout or upload fails: the runner cannot reach \texttt{https://git.ssw590-g1.tech}; check DNS and the Caddy container. An upload error naming ``GHES'' means an artifact action newer than Gitea supports (run~\#1).
\end{enumerate}
\textbf{Check against a real failure.} For run~\#5, steps~1 and~2 led directly
to the cause: the red step was ``Compile the manual'', and the log showed
\texttt{! Undefined control sequence.} followed by
\texttt{l.199 \string\ControlledFailureForRowSix} (\ListRef{66}). Removing that
line (commit \texttt{a9636e4}) gave the green run~\#6. Step~5 matches run~\#1.
